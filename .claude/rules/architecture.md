# Architecture Rules

This file is about **services** (separate processes sharing the Redis queue) and the invariants of each flow. How code is organised *inside* them — layers, ports, where a new module goes — is in [layered-architecture.md](layered-architecture.md), and applies to all new code. Where the two differ for new code (notably "Connectors" below, and the `agent/` layout in "Agent"), the layered-architecture rules win; the sections below describe the current tree and the invariants that survive the migration.

## Service Boundaries

**Receiver** (`src/receiver/`) does exactly two things: verify the Slack signature and enqueue the job. Never add agent logic, Databricks calls, or Supabase reads to this service.

Exceptions, both narrowly scoped to `/slack/interactivity`:
- Its `block_actions` handler calls `views.open` directly instead of enqueuing. Slack's `trigger_id` expires ~3 seconds after issuance — a window the RQ queue can't reliably guarantee under load — and the view is built by a pure function (`agent.forms.access_request_view.build_access_request_view`) from the button's `value` plus the dropdown options the worker snapshotted into Redis (`access_form_options:{token}`) when it posted the button, so no Supabase/Databricks I/O is introduced — only a Redis GET. A button without a readable snapshot is refused like an expired one. Because the button `value` and the snapshot shape are a contract between worker and receiver, change them in one rollout of both. The lookup runs off the event loop on its own Redis client (`form_redis`: 1 s socket timeouts, no retries) under a 1 s overall deadline; if Redis is slow or down the receiver logs and acknowledges the click without enqueuing anything (the queue lives in the same Redis), and the user can click again.
- Its `view_submission` handler runs `agent.forms.access_request_view.validate_submission()` — pure regex format validation, no I/O — synchronously before enqueuing, because Slack requires field errors on the view_submission response itself (`response_action: "errors"`) before the modal closes; an async worker reply would arrive after the modal is already gone. Anything requiring real I/O (the Databricks principal lookup) still happens in the worker task after enqueuing.

A third exception, unrelated to Slack payloads entirely: `GET /secrets/{token}` (alongside `/healthz`) serves a one-time service-principal-secret view via an atomic Redis `GETDEL` — no Slack signature to verify (it's opened directly in a browser by a human, not called by Slack) and no Supabase/Databricks I/O (the secret is already sitting in Redis by the time the link is posted). See "Service Principal Secrets" below.

**Worker** (`src/worker/`) is a thin RQ shell: `tasks.py` loads the bot config, handles Slack-side UX (thinking animation, reply chunking), and calls into `src/agent/`. It owns no agent logic of its own, must not listen on any port, and must not call Slack Event API endpoints directly. The RQ job paths (`worker.tasks.<fn>`) are strings enqueued by the receiver and scheduler — renaming a task function or module breaks jobs already in the queue.

**Agent** (`src/agent/`) owns all agent logic, organised by task:
- `agent.py` (loop), `dispatch.py` (tool routing), `history.py` (thread history in Redis)
- `skills/` — loader (reads the Supabase `agent_skills` table), router, `source.py` (file parsing), `sync.py` (`make skills-sync`, run by the DB Migrate workflow), and the skill files in `skills/files/`
- `forms/` — Slack modal view, form options built from synced datasets, submission validation, `VerifiedAccessRequest` (pure, no I/O)
- `pr/` — `rules_v2.yaml`/PR-template rendering (pure) and `data_platform_repo.py` (the access-control branch/PR workflow on top of `connectors.github`)
- `access_control/` — access-request categories and requests (Supabase), principal lookups, submission, review, and the `request_data_access` tool
- `service_principal_secrets/` — encrypted secret cache and the `generate_service_principal_secret` tool
- `pr_reminders/` — PR approval checks and reminders: pure link parsing / query / status / message / limits modules (a reminder's `ReminderConfig` class lives in `common/configs.py`), `service.py` (Slack + GitHub I/O), and the `check_pr_approvals` / `schedule_pr_reminder` tool handlers
- `schedules.py` — the schedule-CRUD tool handlers
- Migrated to the layered layout (top-level packages, see [layered-architecture.md](layered-architecture.md)): `bots/` (registry), `schedules/` (CRUD + the atomic reminder / dataset-sync inserts, and the `list/add/update/remove_schedule` tool handlers), `characters/` (voices bound to features and skills, see "Characters"), `channel_analysis/` (reading a Slack channel for the agent, see "Channel Analysis"), `dataset_sync/` (generic Databricks → Supabase sync: `core/service.py` has `sync_dataset`, `run_scheduled_sync`, `schedule_sync`; `infra/` the `synced_datasets` store (`get_rows` for readers), Databricks fetcher and Slack notifier; `presentation/tools.py` the `list_synced_datasets` / `sync_dataset` / `schedule_dataset_sync` handlers)

**Connectors** (`src/connectors/`) are generic clients for external tools (Slack, Databricks, GitHub, OpenAI, Redis, Supabase connection/agent_skills). Supabase table modules in `connectors/db/` own their row dataclass and queries (see [database.md](database.md)) — for existing tables; new tables live in the owning feature's `infra/`. They expose raw primitives and carry no task-specific logic — anything that knows about access requests, rules files, or skills belongs in `src/agent/`.

**Scheduler** (`src/scheduler/`) only evaluates cron schedules and enqueues jobs. It must not run the agent itself or post to Slack directly.

Services communicate exclusively through the Redis `slack_events` RQ queue. Never import across service boundaries (receiver ↔ worker ↔ scheduler). `agent/` and `connectors/` are shared libraries, not services; the receiver may import only the pure, I/O-free `agent.forms` (and must not import anything from `agent/` that pulls in OpenAI, Redis or Supabase — keep `agent/__init__.py` and `agent/forms/__init__.py` empty).

## Bot Config

All per-bot configuration lives in the Supabase `bots` table. Never add per-bot env vars. New fields belong in the `bots` table with a migration in `src/migrations/`.

Bot resolution:
- Receiver → `bot_repository.get_by_app_id(api_app_id)` (uses Slack's `api_app_id` field; repository built in `receiver/wiring.py`)
- Worker → `bot_repository().get_by_id(bot_id)` (stored in the enqueued job payload; built in `worker/wiring.py`); the scheduler only reads schedules and passes `bot_id` through

## Redis Key Conventions

| Key pattern | TTL | Purpose |
|---|---|---|
| `seen:{event_id}` | 600 s | Receiver deduplication |
| `chat_history:{thread_ts}` | 24 h | Agent conversation history |
| `scheduler:last_fired:{sha256[:16]}` | 24 h | Scheduler dedup |
| `access_form_options:{token}` | `AgentConfigs.ACCESS_REQUEST_BUTTON_TTL_SECONDS` (1 h) | Snapshot of the data access form's synced dropdown options, written by the worker when it posts the "Open Form" button and read (not deleted) by the receiver on each click; the token is in the button's `value` |
| `secret_link:{token}` | `AgentConfigs.SECRET_LINK_TTL_SECONDS` (600 s) | One-time service-principal-secret view link; read via atomic `GETDEL` in `receiver/app.py`, so it's also deleted the instant it's read |
| `thread_character:{channel}:{thread_ts}` | `AgentConfigs.THREAD_CHARACTER_TTL_SECONDS` (14 days) | The character picked for a thread, so agent replies and PR reminders in it keep one voice; written by `characters/infra/redis_thread_characters.py`, read on every reply and reminder in the thread. Unreadable or unwritable means a fresh pick, never an error |
| `slack_no_customize:{sha256(token)[:16]}` | `connectors/slack.py::_NO_CUSTOMIZE_TTL_SECONDS` (10 min) | Marks a Slack app whose token lacks `chat:write.customize`, so `post_message` stops asking for a custom name and icon (each ask would cost a refused call and a retry) until the key expires; `rq worker` forks a process per job, which is why this is in Redis and not in memory. Unreadable means ask again, never an error |

Do not add ad-hoc Redis keys outside these patterns without updating this table.

Note: the data access request button's TTL (`AgentConfigs.ACCESS_REQUEST_BUTTON_TTL_SECONDS`) is embedded as an `expires_at` timestamp in the Slack button's own `value` payload, not a Redis key — the receiver just compares it against the current time.

## Databricks Client

`src/connectors/databricks/` (`sql.py` specifically) must:
- Reject any SQL that is not a SELECT statement
- Enforce 200-row result cap (show truncation note when exceeded)
- Use wait_timeout=50 s, on_wait_timeout=CANCEL on the Statement API
- Never expose raw connection credentials — the PAT comes from the env, not from Supabase

## Agent Loop Invariants

- Max 10 tool-call iterations per request
- Conversation history trimmed to last 20 user/assistant pairs before saving
- Schedule-management tools (`category="schedule"`) are admin-only; check `bot.admin_users` before execution. They are also scoped to the calling bot: list/update/remove only see that bot's schedules plus legacy rows with `bot_id IS NULL` (which run under the `default` bot), so one bot's admin can't touch another bot's schedules. `schedule_pr_reminder` is in this category too, so it gets the same admin check; `update_schedule` only edits `kind = 'question'` rows, so it can't bypass a reminder's interval check
- Dataset sync tools (`category="dataset_sync"`: `list_synced_datasets`, `sync_dataset`, `schedule_dataset_sync`) are admin-only (`bot.admin_users`), like the schedule tools. Datasets are workspace-wide, so these tools are not scoped to the calling bot
- The `check_pr_approvals` tool (`category="pr_reminder"`) is open to any user and only reads the channel the request was made in
- The `request_data_access` tool (`category="data_access"`) is channel-gated instead — it checks the Supabase `access_request_categories` table (`bot_id` + `request_type` + channel membership), not `admin_users`
- The `generate_service_principal_secret` tool (`category="secrets"`) is gated by **both** channel and reviewer membership from `access_request_categories` (`request_type="service_principal_secret"`) — unlike `data_access`, the requester themselves must be a listed reviewer; there's no separate approval step
- Character tools (`category="characters"`: `list_characters`, `add_character`, `update_character`, `remove_character`) are admin-only (`bot.admin_users`), like the dataset sync tools, and not scoped to the calling bot: characters are workspace-wide
- Channel analysis tools (`category="channel_analysis"`: `check_channel_access`, `read_channel_messages`, `read_channel_file`, `analyze_channel`) are admin-only (`bot.admin_users`). A run with no requester (a scheduled question) has `user_id=None`; it may use them only because `process_scheduled_question` passes `UnattendedRun({"channel_analysis"}, run_as)` to `run_agent`: the tools then run with the schedule's `run_as` admin (`schedules.run_as`, set when a schedule is created or edited) as the requester, re-checked as an admin and, for a private channel, as a member on every run; a schedule with no `run_as` is refused. That never opens any other admin category. Once a run has read channel or file content (`dispatch.UNTRUSTED_CONTENT_TOOLS`), the rest of that run is offered and may run only `dispatch.READ_ONLY_TOOLS`: text in a channel is not the admin's, so it must not be able to make the agent remove a schedule or add a character. `execute_query` is not in that set while `connectors/databricks/sql.py` only checks for a leading SELECT / WITH
- Authorization status (is_admin) is prepended to the question text, not stored in history

## Adding Tools to the Agent

New OpenAI tool schemas go in `AgentConfigs.TOOLS` (`src/common/configs.py`) as an `AgentTool(...)` entry with a `category` (`"core"`, `"schedule"`, `"data_access"`, `"secrets"`, `"pr_reminder"`, `"dataset_sync"`, `"characters"`, or `"channel_analysis"`). The corresponding dispatch branch goes in `dispatch_tool()` in `src/agent/dispatch.py` (which routes by category to `dispatch_schedule_tool()` in `schedules/presentation/tools.py` / `dispatch_data_access_tool()` in `agent/access_control/tools.py` / `dispatch_secret_generation_tool()` in `agent/service_principal_secrets/tools.py` / `dispatch_pr_reminder_tool()` in `agent/pr_reminders/tools.py` (also reached from the `schedule` category for `schedule_pr_reminder`) / `dispatch_dataset_sync_tool()` in `dataset_sync/presentation/tools.py` / `dispatch_character_tool()` in `characters/presentation/tools.py` / `dispatch_channel_analysis_tool()` in `channel_analysis/presentation/tools.py` (these four take their repository / service from `ToolServices`, built in `worker/wiring.py`; `dispatch_pr_reminder_tool` takes the `CharacterService` from there too) / inline core handling). OpenAI calls go through `src/connectors/openai_client.py`. Keep tool names snake_case and match them exactly between the `AgentTool` entry and the dispatch branch.

## Skill Routing

Skill text is loaded by `load_all_skills()` from Supabase only (`connectors/db/agent_skills.py`); the files in the image are just the input to `make skills-sync`, and an empty table fails the request. `skills/sync.py` imports only `source` and the `agent_skills` connector (not the router/OpenAI) so CI can run it without an OpenAI key.

Router calls must use `response_format={"type": "json_object"}` so the response is always parseable. If the router call fails for any reason, fall back to loading all enabled skills — never block the request.

## Data Access Requests

A parallel, mostly-deterministic flow alongside the main agent loop, for requesting and approving access to Databricks tables/row filters:

1. **Request** — the `request_data_access` tool (`dispatch_data_access_tool` in `src/agent/access_control/tools.py`) checks the `access_request_categories` table for the bot/channel/request_type, snapshots the form's dropdown options from the synced datasets (`store_locations`, `row_filter_tags` — see "Synced Datasets") into Redis (`stash_form_options`; it refuses, without posting, if a dataset was never synced or can't make a valid form), then posts a Slack button. The button's `value` carries the request metadata (including `reviewers`, an `expires_at` and the `options_token`) — nothing is written to Supabase yet.
2. **Form** — `block_actions`/`view_submission` on `/slack/interactivity` are the receiver's two documented exceptions above; the actual insert happens after enqueuing, in `worker.tasks.process_data_access_submission` (which calls `agent.access_control.submission.submit_data_access_request`), which writes a `pending` row to `access_requests` (`src/agent/access_control/access_requests.py`) with a 24 h `expires_at`.
3. **Review** — a reviewer replies `approve <id>` / `reject <id>` in the thread. `reply_to_mention` (`src/worker/tasks.py`) detects this prefix and routes to `agent/access_control/review.py::handle_review_decision` (after `parse_review_command` recognises the prefix) **before** the LLM agent loop runs — approval/rejection is exact-keyword control flow, not an LLM tool call. It re-validates channel eligibility and reviewer membership (`user_id in row.reviewers`) at approval time, not just at submission time.
4. **Approval** — resolves the principal via Databricks (`agent/access_control/principals.py` or `service_principals.py`, on top of `connectors/databricks/scim.py`), renders the `rules_v2.yaml`/`service_principals.yaml` snippets (`src/agent/pr/access_control_rules.py`), and opens (or reuses) a PR on `100xteam-ai/vireox-data-platform` via `src/agent/pr/data_platform_repo.py` (on the generic `src/connectors/github.py`) — one branch/PR per `ticket_id`, check-then-create so retries and duplicate approvals never create duplicate branches, files, or PRs. The bot's approval only opens the PR — it does not merge it. `handle_review_decision`'s reply (`src/agent/access_control/review.py::_approve`) tells the reviewer that merging the PR on GitHub is the remaining step: merging to the base branch triggers `vireox-data-platform`'s own CI/CD, which deploys the change to production (GA) automatically.

**GitHub client** (`src/connectors/github.py`) follows the same credential rule as the Databricks client: the credentials (GitHub App id/private key, preferred, or the PAT `GIT_REPO_PAT_DATA_PLATFORM`) come from the env, never from Supabase.

## Service Principal Secrets

A synchronous, single-turn flow (no form, no separate approval step — unlike Data Access Requests above) for reviewers to self-serve a Databricks service-principal OAuth client secret:

1. **Dispatch** — `generate_service_principal_secret(service_account)` (`dispatch_secret_generation_tool` in `src/agent/service_principal_secrets/tools.py`) first validates `service_account` against the same `EMAIL_PATTERN` regex used by `agent/forms/access_request_view.py`, then checks the `access_request_categories` table (`request_type="service_principal_secret"`) for **both** channel eligibility and that the requesting user is a listed reviewer — refusing immediately if any of these fail.
2. **Lookup** — verifies the service principal exists via `agent/access_control/principals.py::find_service_principal_by_email`; refuses politely if not found. No Databricks/Supabase writes happen before this point.
3. **Cache check** — `agent/service_principal_secrets/store.py::get` looks up a cached row (keyed by `email`, the bare address, which is the table's unique constraint — not scoped by `bot_id`, since the same service principal can be requested via more than one bot; and not `client_id`, since a service principal can be deleted and recreated for the same user, getting a new `client_id` in the process). Databricks only ever returns a secret's plaintext once, at creation, so this table stores it encrypted (`common/crypto.py`, Fernet, key from `Configs.SECRET_ENCRYPTION_KEY`) to make "return the existing secret if still valid" possible at all. If the cached row is `status == "ACTIVE"` and unexpired, it's decrypted and reused — no new Databricks secret is minted (Databricks caps active secrets per service principal).
4. **Mint** — otherwise, `connectors/databricks/service_principal_secrets.py::create_secret` requests a new one; the flattened response is cached via `upsert` (encrypted) for next time.
5. **Hand-off** — a fresh random token is written to Redis (`secret_link:{token}`, see the Redis table above) holding the **full flattened record** (`id`, `secret`, `secret_hash`, `status`, `create_time`, `update_time`, `expire_time`, `service_account`, `client_id`, `email` — the same shape Databricks itself returns) as JSON, with a short TTL, and a plain link (no button) is posted to Slack. `GET /secrets/{token}` on the receiver (documented exception above) serves it exactly once via atomic `GETDEL`, then it's gone — this is deliberately re-generated on every request (cache-hit or not) so a cached-valid secret still gets its own fresh, single-use link rather than reusing a stale one.

Out of scope for now: revoking the previous Databricks secret on rotation (a `delete()` method exists on the same proxy API if this becomes necessary), and reconciling the cached `status` against a live Databricks listing (an invalid/expired cache entry simply triggers a fresh mint).

## Synced Datasets

Generic, reusable module (`src/dataset_sync/`) that copies slowly-changing reference data from Databricks into Supabase, so features read it from our own database instead of hard-coding it or querying Databricks live. Design and the form it feeds: [docs/data_access_request_form.md](../../docs/data_access_request_form.md) ("Form Option Data").

1. **Registry + storage** — one `synced_datasets` row per dataset (`dataset`, `description`, `source_sql`, `enabled`, `column_names`, `synced_rows`, `row_count`, `last_synced_at`, `last_status`, `last_error`). Workspace-wide, not per bot. Adding a dataset is an INSERT (no deploy); the SQL is run with the bot's Databricks PAT, so write access to this table is as sensitive as the PAT.
2. **Sync** — `DatasetSyncService.sync_dataset(dataset, force=False)` (`dataset_sync/core/service.py`) runs `source_sql` through `connectors/databricks/sql.py::fetch_rows` (the uncapped, read-only-guarded sibling of `run_query`: SELECT/WITH only, 50 s timeout, `MAX_ROWS` (`dataset_sync/core/limits.py`) hard limit that errors instead of truncating — the 200-row cap above applies to `execute_query`, not here) and **fully replaces** the snapshot in a single UPDATE. The whole read/query/validate/save sequence runs under a per-dataset transaction-scoped advisory lock (`DatasetRepository.lock`, implemented by `SupabaseDatasetRepository.lock`, non-blocking: a concurrent sync is refused, a scheduled tick that finds one running is silent), so manual and scheduled syncs can't overwrite each other. A query that returns duplicate column names is refused. A failed query, an empty result, or (unless `force`) a result under `SHRINK_GUARD_RATIO` of a dataset of at least `SHRINK_GUARD_MIN_ROWS` rows (same module) leaves the previous snapshot untouched and only records `last_status = 'error'` / `last_error`.
3. **Reading** — consumers call `store.get_rows(dataset)`, which returns the last good snapshot (a failed later sync doesn't break readers) or raises `DatasetNotSyncedError`.
4. **Scheduling** — a `schedules` row with `kind = 'dataset_sync'`, `config = {"dataset": ...}` and `channel` = where failures are reported. The scheduler enqueues `worker.tasks.process_dataset_sync(schedule_id, bot_id)` (no RQ retry; the next tick is the retry), which runs `DatasetSyncService.run_scheduled_sync` (`dataset_sync/core/service.py`): silent on success, a Slack post to the schedule's channel on failure. At most one active recurring sync per dataset (workspace-wide, but `remove_schedule` is bot-scoped, so the tool tells an admin of another bot to change it through its owner) (`schedules/infra/supabase_schedules.py::add_dataset_sync`, advisory-locked); minimum interval `MIN_INTERVAL_MINUTES` (`dataset_sync/core/limits.py`), validated by `common/cron.py`. `update_schedule` only edits `kind = 'question'` rows, so it can't touch a sync; `remove_schedule` stops one.
5. **On demand** — the admin-only `list_synced_datasets` / `sync_dataset` / `schedule_dataset_sync` tools; the agent skill `14_dataset_sync.md` tells the model to gather the dataset, cadence and failure channel before calling and to ask when unclear.

## Characters

Voices the bot speaks in (`src/characters/`), stored in the Supabase `characters` table. Design: [docs/characters.md](../../docs/characters.md).

1. **Row** — `name`, `display_name` / `icon_emoji` / `icon_url` (the Slack sender name and icon), `enabled`, `bindings`, `persona`, `voices`. A binding is `feature:<name>` (messages code posts from templates, the character's `voices[<name>]` block supplies them; `pr_reminder` is the only feature so far) or `skill:<name>` (agent replies shaped by that skill, the `persona` joins the system prompt). Workspace-wide, not per bot. The seed files in `src/characters/files/` ship in the image and only fill the table: the worker runs `python -m worker.seed_characters` when it starts (`entrypoint.sh`), which inserts names that are missing and never changes or deletes a row (a failure is logged and never stops the worker). After that the table is the source of truth. Admins add, change (including bindings, which is the scope of a character: the features and skills it speaks for), disable and remove characters by asking the agent (`add_character` / `update_character` / `remove_character`; add needs a name, a display name and a binding, and add and update take `dry_run` so the agent validates a request before it stores it; every result is re-validated and add never overwrites), or directly in Supabase. A character with a seed file that is removed comes back on the next deploy, so the agent offers `enabled = false` instead.
2. **Validation on every read** — rows can change in Supabase without a sync, so `characters/core/validation.py` runs each time a character is loaded (`CharacterService._usable`). A row that fails is skipped with a warning, and `list_characters` marks it invalid with the reason. A template may use only the placeholders of its field, no attribute or index, no `<` or `>`, no link with a scheme, `www.` or `mailto:` (a bare domain is not caught), no `@channel` / `@here` / `@everyone`, at most 300 characters; a wrong shape in a hand-edited row (`voices` that is not an object, a binding that is not a text) is a validation problem and never an exception, and the table has check constraints for the same two shapes; this keeps the invariant that the only live mentions in a reminder are the validated user IDs. Write access to the table decides what the bot posts, so it is as sensitive as write access to `agent_skills`.
3. **PR reminders** — `check_and_remind` asks `CharacterService.character_for_feature("pr_reminder", channel, thread_ts)` once per thread it posts in, renders with `PrReminderVoice.from_character(character)` (a field a character leaves out falls back to `DEFAULT_VOICE` in `message.py`) and posts under the character's name and icon. Reminders stay deterministic: no LLM writes them. The expiry and unreadable notes use the origin thread's character.
4. **Agent replies** — `run_agent` asks `character_for_skills(routed, always, channel, thread_ts)` after the router picked skills: characters bound to a routed skill first, else those bound to an always-loaded skill (`skill:core` is the default voice for every task), else none. The persona is appended to the system prompt after a fixed `## Voice` block (`characters/core/persona.py`) that keeps SQL, identifiers, numbers, URLs, tool arguments and tool permissions out of the persona's reach. `summarize_answer` and scheduled questions take the same character.
5. **One character per thread** — the pick is stored in Redis (`thread_character:{channel}:{thread_ts}`, 14 days) and reused while the character stays enabled and valid, by reminders and replies alike, so a thread keeps one voice. A stored character without a `pr_reminder` voice is not used for a reminder and is not overwritten.
6. **Fail open** — an unreadable table or thread store means the default voice, never a failed reminder or reply.
7. **Sender identity** — `connectors/slack.post_message` takes `username` / `icon_emoji` / `icon_url` (Slack's `chat:write.customize`); without the scope it posts as the bot. `chat.update` can't change a sender, so when an agent reply has a character the worker (`reply_to_mention`) posts new messages under it and deletes the thinking placeholder; without one it updates the placeholder in place. A scheduled question's header, posted before the router runs, stays under the bot's name.

## Channel Analysis

Lets an admin have the agent read a Slack channel over a period and report insights (counts, comparisons, what is missing, themes). Package `src/channel_analysis/`. Design and use cases: [docs/rfc_channel_analysis.md](../../docs/rfc_channel_analysis.md).

1. **Access first, enforced in code** — `check_channel_access` returns every problem found, for the bot (member, history and read scopes, `files:read` as a warning) and for the requester (a private channel needs the requester to be a member; a public one needs nothing). The agent is told to call it first, but `read_channel_messages` and `read_channel_file` redo the same checks on every call (`ChannelAnalysisService._require_access`), so skipping the check, or an injected call, can't read a private channel. A scheduled run has a requester too: the schedule's `run_as` admin (see Agent Loop Invariants), so the private-channel check applies to it on every run. The history probe in `check_access` runs only when nothing blocks, so a refused check can't reveal whether a channel has messages. The wording of each problem is `core/errors.py::ACCESS_MESSAGES`, shared by the check and the read errors.
2. **Reading** — `read_channel_messages(channel, lookback_days, end_days_ago, contains, include_replies, before)`. The window reaches at most `MAX_REACH_DAYS` (30) back from now. Pages are newest first and cursor-paged by message timestamp (`before`, which Slack's `latest` takes exclusively), not Slack's cursor, so a page is stateless; a result's `before` is `<ts>@<window start>`, so every page of one window has the same bounds however long the paging takes (the carried start is checked against the reach, so a made-up token can't read further back). `read` and the scan it consumes (`_scan`, a generator) are separate so another consumer can reuse the scan. The text filter runs in `core` after the fetch, so one call can scan up to `MAX_SCAN_PER_CALL` messages to fill a page; a page ends at `PAGE_CHAR_BUDGET` characters and the result always says how many messages it holds and whether the window is finished. Thread replies are read by default (one `conversations.replies` call per thread, at most `REPLIES_FETCH_MAX` messages, hence the smaller batch; a thread that can't be read is shown with its reply count, not a failed page). The scan cap counts the messages Slack returned, noise included. A channel name is resolved once per run (cached in `SlackChannelHistory`), and the agent is told to use the ID after the check. A rate-limited thread is retried once after Slack's `Retry-After` (capped at 30 s) and then shown with its reply count and no replies, so a page doesn't fail for it. Noise subtypes (joins, topic changes) are dropped in `infra`.
3. **Flattening** — bot reports keep their content in blocks and attachments; `infra/message_text.py` turns text, header / section / context / rich-text blocks, attachments, files (as `[file F…: name, type, size]`), reactions and the author into text. A message's link is built from the workspace URL (`auth.test`) and the `ts`.
4. **Files** — `read_channel_file(channel, file_id, offset)` reads a file attached to a message: CSV, TSV, text, JSON, logs, PDF with a text layer (`pypdf`), Excel `.xlsx` (`openpyxl`). The download URL comes from `files.info`, never from the model, and `connectors/slack.py::download_file` sends the token only to https hosts on slack.com. A file must be shared in the channel that passed the checks, and is refused over `FILE_MAX_BYTES` before download. Text is paged at line boundaries (a CSV header repeats on later pages unless it takes over a quarter of a page). A PDF or a workbook is parsed in a child process (`infra/file_parser.py` runs `python -m channel_analysis.infra.file_text`) with memory, CPU and time limits, because a file under the download limit can unpack to far more; a workbook is also refused before it is opened if its archive unpacks to over `XLSX_MAX_UNCOMPRESSED_BYTES`. The adapter keeps the last file's text in memory (one forked process serves one agent run) so paging doesn't download it again.
5. **Scheduled** — an admin schedules a self-contained question; `add_schedule` / `update_schedule` record the admin as `schedules.run_as` (V16) and the scheduler hands it to the job. The run reads channels as that admin, checked on every run (see Agent Loop Invariants). A scheduled run that can no longer read the channel posts the problem in its answer.
6. **Untrusted content** — see Agent Loop Invariants: after a channel or file read, only read-only tools remain for that run (`agent/agent.py`, enforced both by not offering the schema and by refusing the call; an answer saved to the thread history after such a read is prefixed `agent.agent.UNTRUSTED_ANSWER_MARK` by code, and `run_agent` replaces every marked answer with `UNTRUSTED_ANSWER_REMOVED` when it loads the thread's history, so the next request, which has every tool again, never sees text that came from a channel; the admin's own questions stay).
7. **Job timeout** — a mention job and a scheduled-question job are enqueued with `job_timeout=600` (it was 120): a multi-page read with a model call between pages takes minutes.
8. **Analysis (`analyze_channel`)** — for counts over more messages than a request can read. It shares the access checks, the window and the paging scan (`_scan`) with `read`, but instead of returning pages it turns the messages (and, with `include_files`, pieces of their files, read once each and at most `MAX_FILES_PER_CALL` per call) into numbered *items*, packs them into chunks of `CHUNK_CHAR_BUDGET` (at most `MAX_CHUNKS_PER_CALL` a call; a message that doesn't fit is left for the next call through `next_before`, and the first message of a call is always taken so a call progresses), and has a cheaper model (`Configs.EXTRACTION_MODEL`, default `ROUTER_MODEL`, behind the `ExtractionModel` port, `infra/openai_extraction.py`, no tools) fill the records the admin described, `EXTRACT_PARALLELISM` chunks at a time. `core/extraction.py` (pure) builds the prompt, checks every record (an item the chunk has, declared fields only, `allowed_values` enforced, values cut) and counts in code per group: records, distinct messages, distinct UTC dates, links of the newest messages. A wrong-shaped answer is asked once more; a failed chunk is reported by its time range and left out of the counts, and over half failing makes the result `unreliable`. The agent sees counts, a sample and links, never raw messages, but a crafted post can still bias a count, so `analyze_channel` is one of `UNTRUSTED_CONTENT_TOOLS`. Each call logs its tokens and time at INFO (`analyze channel=… prompt_tokens=… completion_tokens=… chunk_seconds=[…]`). The limits are untuned constants in `core/limits.py`.
9. **Slack scopes** — `channels:history`, `groups:history`, `channels:read`, `groups:read`, `files:read` (reinstall the app after adding). A missing scope is reported with Slack's `needed` value and never crashes the run.

Not built yet: map-reduce extraction for channels too busy for one request (phase 2 in the RFC); the signal is an answer that says it covered only part of the window.

## PR Review Reminders

Design: [docs/pr_review_reminders.md](../../docs/pr_review_reminders.md). Checks whether GitHub PRs shared in Slack are approved and mentions the people the requester names in the thread where each PR was shared. A request that names nobody is refused with "Who should I remind?" and the agent asks.

1. **One-off** — `check_pr_approvals(scope, lookback_hours?, pr_urls?)` reads the thread (`conversations.replies`) or the channel's recent top-level messages (`conversations.history`), extracts PR links (also from attachments and blocks), asks GitHub for `reviewDecision` in one GraphQL query, and posts one reminder per thread that has a PR waiting for review. The tool posts the reminders itself (the LLM never rewrites them) and returns a short summary for the agent to relay.
2. **Recurring** — `schedule_pr_reminder(cron, scope, mentions, ...)` inserts a `schedules` row with `kind = 'pr_reminder'` and its settings in `config` (`common/configs.py::ReminderConfig`), (the duplicate check, the per-channel quota and the insert happen in one transaction under an advisory lock; a repeated request returns the existing reminder instead of creating another: same bot, watched channel, scope and people, plus the thread for thread scope), then, if now is inside the hours and days of the cron, runs the check once (a failure before anything is posted removes the row; a failure only in saving progress keeps it, since the reminders name it); otherwise the first tick does it. The schedule is kept even if nothing is waiting yet (a PR can be shared later); only a failed first check removes it. The scheduler enqueues `worker.tasks.process_pr_reminder(schedule_id, bot_id)` instead of `process_scheduled_question` for those rows; the worker runs `agent/pr_reminders/service.py::run_reminder`, which involves no LLM.
3. **Stopping** — `run_reminder` soft-deletes the row (`status` becomes `completed` or `expired`; the scheduler only loads `active` rows) only when `config.expires_at` has passed (set from the optional `expires_in_hours` argument, which the agent passes only when the user asks for a time limit), on a malformed `config`, or when the channel became unreadable. A reminder is permanent by default: nothing waiting never ends it, since new PRs keep being shared. An admin stops one with `remove_schedule`, which hard-deletes. When a reminder may post is part of its cron (hours and days), read by the scheduler in the row's `schedules.timezone` (default `Asia/Ho_Chi_Minh` for reminders, `UTC` for everything else); the agent skill writes working time, weekdays 08:00–17:59 (`*/30 8-17 * * 1-5`), unless the requester says otherwise. There is no clock check in `run_reminder`; only the first check at scheduling time reads the cron window (`limits.is_within_cron_window`), never a user's `check_pr_approvals` request. Reminder jobs are enqueued without RQ retries (a run posts before it saves progress, so a retry would repeat the mentions); a transient failure fails the job and the next tick is the retry, and a failed Slack post is only logged. A thread reminded less than half the minimum interval ago is skipped (a tick fired seconds after the first check must not repeat it). At most `PR_REMINDER_MAX_THREADS_POSTED` threads are reminded per run: the ones reminded longest ago first (`config.last_reminded`), so they take turns.

**Finished PRs** get a reaction on the Slack message that shared them: `white_check_mark` (approved or merged) or `x` (closed without merging) (`service._mark_finished`, called at the end of `check_and_remind`, so both the one-off tool and every scheduled tick do it). Slack's `reactions:write` scope is needed. A message already carrying either emoji from anyone is skipped (read from the `reactions` array of the scanned messages, no extra API call), a message is marked only when every PR it links finished the same way (judged on all of the message's PRs, `PrLink.message_refs`, even those whose newest mention is in a later message; a mix of merged and closed gets nothing), when a PR is linked in several messages only the newest is marked, PRs typed in a request are never marked, and a failure is only logged: reacting must not stop the reminders.

Invariants: the only live mentions a reminder can contain are the user IDs that passed `limits.parse_mentions` (user mentions only, at most 10 — never `@channel`, `@here` or a user group), rendered in `agent/pr_reminders/message.py`, where text from GitHub is escaped (the default wording is `DEFAULT_VOICE` in that module, a character can replace it, and the parts no character changes are the `ReminderMessages` config class in `common/configs.py`). `worker.tasks.reply_to_mention` strips only the bot's own mention, so the requester's @mentions reach the agent. The bot's own messages are skipped when scanning (matched on `app_id`), or its reminders would keep PRs "alive". The reminder job reuses the existing `scheduler:last_fired:{sha256[:16]}` Redis key pattern (hashing `pr_reminder:{id}:{cron}`), so no new key.
